# fmodex-midi: design

## 1. Goal

When a 32-bit FMOD Ex 4.32.1 host plays a MIDI sound, send the notes to a real MIDI device instead of FMOD's built-in DLS synth. Use KDMAPI (OmniMIDI) when it's available, otherwise winmm. Everything else must behave exactly as stock. Non-MIDI sounds are never touched, and any internal failure falls back to stock FMOD playback.

Not in scope: positional (3D) MIDI, surround, DSP/reverb on MIDI, reverse playback (it falls back to stock).

## 2. Facts about FMOD Ex 4.32.1 (x86)

- `fmodex.dll` exports 702 names: 340 C `FMOD_*`, 362 MSVC-mangled C++ names, plus a few internals. The list is in `references/fmodex-4.32.1/exports.txt`.
- C++ hosts call the mangled member functions (`?playSound@System@FMOD@@QAG...`). `QAG` means public `__stdcall`, so `this` is the first stack argument, and a hook is a plain `__stdcall` free function with `this` first. C++ `bool` parameters take a 4-byte slot, and only the low byte counts.
- `FMOD_CREATESOUNDEXINFO` is 0x7c bytes in the 4.32 layout. We read only `cbsize` (+0) and `length` (+4).
- `Sound::getFormat` reports type 11 (`FMOD_SOUND_TYPE_MIDI`) for MIDI. The frequency at `playSound` (`getFrequency`) is the mixer rate, e.g. 48000, and hosts express speed changes relative to it.
- FMOD's reported MIDI length runs a little past the file's End-of-Track (it includes a release tail).
- Hosts may **delay-load** `fmodex.dll`, so the DLL, and the `fmodex_real.dll` its forwarders point at, may only load on the first FMOD call.

The build uses no FMOD SDK files: `src/fmod_min.h` is our own minimal subset of the public API.

## 3. Architecture

### 3.1 Proxy DLL

Install by renaming the host's `fmodex.dll` to `fmodex_real.dll` and putting ours in its place.

- `fmodex.def` is generated by `tools/gen_def.py` from the export list. Every export forwards to `fmodex_real.<name>`, except the names in `src/hooks.txt`, which map to `hk_<Class>_<method>`.
- `make check` verifies three things:
  - the export set equals the original's, and every forwarder targets the same name;
  - imports are only `kernel32`, `msvcrt` and `winmm`;
  - each hook's `@N` stdcall size matches the argument count in its mangled name. A mismatch would corrupt the host's stack.
- `DllMain` only calls `DisableThreadLibraryCalls`. On the first hook call, init reads the config, opens the log, and `LoadLibraryExW`s `fmodex_real.dll` from our own directory, since it isn't guaranteed to be mapped yet (delay-load). It then resolves the real functions. None of this runs under the loader lock.
- No IAT patching, no inline hooks, no writable code.

### 3.2 Mute and mirror

For a MIDI sound, FMOD plays the channel exactly as it would have, but **muted**. Everything the host relies on keeps its stock behaviour: END callbacks, `isPlaying`, `getPosition`, channel reuse and stealing. We mirror state changes onto our own voice.

Escape hatch: if a sound can't be handled (reverse playback, a parse failure, no backend), the channel is unmuted, its voice is dropped, and it plays stock.

### 3.3 Hooks (`src/hooks.c`)

| Hook | Behaviour |
|---|---|
| `System::createSound` | Calls the real function. If `FMOD_OPENMEMORY` and the data is an SMF (`MThd`, or RIFF `RMID`), parses it into a refcounted song keyed by `Sound*`. Starts the engine lazily. |
| `System::playSound` | Calls the real function. For a registered song: `setMute(true)` on the FMOD channel, create a Prepared voice, record f0. `FMOD_CHANNEL_REUSE`, or a recycled handle, frees the old voice. |
| `Channel::setPaused` | `false` on a Prepared voice starts it; otherwise pause or resume. Effective paused = channel paused OR master paused. |
| `Channel::setVolume` / `setMute` | Gain = volume × !mute × master volume × !master mute. The FMOD channel always stays muted, whatever the host asks. Hosts commonly re-send `setMute(false)` on every update. |
| `Channel::setFrequency` | Tempo ratio = f / f0 × master pitch, clamped to ≤ 16. f < 0 takes the escape hatch. |
| `Channel::setPosition` | MS or PCM (via f0) → seek, chasing program, CC, RPN and bend state. |
| `Channel::setMode` | Loop flag (`FMOD_LOOP_NORMAL`/`BIDI`). |
| `Channel::stop`, `Sound::release` | Free the voice / drop the song (voices hold their own references). |
| `ChannelGroup::*` on the master group | Global volume, mute, pause, pitch, stop. |
| `System::update` | Our tick on the host's thread: reap voices whose FMOD channel ended (real `isPlaying`), notice an asynchronous backend failure, flush the log. |
| `System::release` | Shut the engine down. |

Locking: one SRWLOCK guards the sound and channel tables. **Never call real FMOD while holding it**, because channel callbacks run inside `System::update` and the host may re-enter our hooks from them.

### 3.4 Engine (`src/engine.c`)

- One sequencer thread owns the backend and every voice. Hooks only queue commands (SRWLOCK queue + auto-reset event) and never block on it.
- The backend is opened **on the sequencer thread**, because a KDMAPI/winmm open can take 0.1–0.5 s. If it fails, queued work is dropped and the hooks hand every channel back to FMOD on the next update.
- Timing uses absolute QPC deadlines and a high-resolution waitable timer (with a `timeBeginPeriod(1)` fallback). Events due within 0.5 ms are sent together.
- Cutover policy: one device has 16 MIDI channels, so the most recently started voice owns it. A newer voice cuts the older one (notes off, reset controllers), while the older FMOD channel carries on, muted.

### 3.5 Player and parser (`src/player.c`, `src/smf.c`): portable C

- SMF formats 0 and 1, PPQ or SMPTE division, running status, an integer tempo map, SysEx and `F7` escapes, and RIFF RMID unwrapping. Input is capped (8 MiB, 1 M events, 1 MiB SysEx).
- Parsing is untrusted-input safe: a malformed file means "not registered" (stock playback), never a crash. Truncation is tolerated; bad status or data bytes are rejected.
- The player keeps shadow state per channel (program, CCs, RPN 0–2, bend, sounding notes) to support explicit note-offs on pause/stop, state re-send on resume, and state chasing on seek.
- Looping is gapless. A loop shorter than 100 ms is played with a 100 ms period, and a service call wraps at most once, so a few-µs looping song can't flood the synth.
- Gain is applied to CC7 (`cc·√gain`, the GM curve, or linear), rate-limited to 50 Hz.

### 3.6 Backends (`src/backend.c`)

- **KDMAPI:** `OmniMIDI.dll`, loaded from System32 (SysWOW64 for us) only. `IsKDMAPIAvailable` → `InitializeKDMAPIStream`; `SendDirectData`; SysEx goes Prepare → `SendDirectLongData` → Unprepare; teardown is `ResetKDMAPIStream` + `TerminateKDMAPIStream`.
- **winmm:** the mapper, an index, or a name substring. SysEx is sent synchronously via `midiOutLongMsg` with an `MHDR_DONE` wait. Close is `midiOutReset` + `midiOutClose`.
- **log:** `t_us HEX…` lines, used by the tests.
- `auto` = KDMAPI, else winmm, else stock FMOD everywhere.

## 4. Testing

- **Native (`make test`):** the parser matches `mido` on every fixture (RMID included); the player is unit-tested on a virtual clock; a truncation/bit-flip fuzz smoke runs under ASan/UBSan.
- **Fuzzing (`test/fuzz.sh`):** libFuzzer + ASan/UBSan over the parser and the player (start offset, pause/resume, ratio, seek, loop), with invariant checks.
- **Integration (`test/integ/`):** a mock `fmodex_real.dll` plus a harness that drives the proxy through the mangled exports the way a typical host does. 11 scenarios: basic, pause, stop, cutover, reverse, corrupt, wav, master, loop, seek, backendfail. Runs under Wine, or in a Windows VM via `RUNNER=vm VM_RUN=…`.
- **KDMAPI (`test/kdmapi/`):** a mock `OmniMIDI.dll` in the Wine prefix's syswow64. The stream must equal the log backend's, and SysEx must be sent prepared.
- **Timing (`midiplay.exe` + `tools/timing_check.py`):** log-backend output vs the `mido` reference. On Windows 10, p99 error was 0.5–0.66 ms.
- **Verified on a real host** (Windows 10 VM): every mirrored behaviour; FMOD's MIDI silent with the proxy and audible again through winmm and through KDMAPI/OmniMIDI 14.8.5 (captured audio envelopes match stock); a 10-minute soak with flat handle and memory counts.

## 5. Not done / ideas

- Positional MIDI: CC10 pan plus CC7 attenuation from the 3D attributes.
- DSP/reverb → CC91; multiple simultaneous MIDI voices on separate devices or ports.
- Other FMOD Ex builds: a different export set needs its own export list, and probably a hash entry in the installer.
